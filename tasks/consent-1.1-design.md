## 1. 機能仕様の確認と曖昧点の質問

### Q1. 匿名試用を続けるか（§3-2）→ **同意を課して続ける**

弁護士は「IP・端末情報・Cookie・セッションID・アクセスログとチャット入力が相まって個人を識別できる場合は個人情報に該当する」とし、匿名ユーザーにもチェックボックス3つでの同意取得を推奨。当方の推奨は「同意を課す」。廃止すると初回体験がゼロになり、ベータ獲得の入口を失うため。

以降の設計は **同意を課す** 前提で書いている。廃止を選ぶなら §2 以降はほぼ全部不要になり、`AnonSignInButton` と関連導線の削除だけで済む。

### Q2. 匿名ユーザーの同意ログはいつまで残すか（**設計上の急所**）→ **(a)**

現状 `consent_logs.user_id` は `profiles(id) ON DELETE CASCADE`。一方 `scripts/purge-anon-users.ts` が匿名 auth ユーザーを削除する運用になっている。つまり匿名の同意ログを作っても、purge の時点で証跡ごと消える。

これはプラポリ第6条「利用規約への同意ログは法的証拠として削除請求後も保管します」と正面から矛盾する。同意を取る意味は証跡が残ることなので、ここを決めないと 2-5 は形だけになる。

選択肢:

- (a) 同意ログを `profiles` から切り離す。`user_id` の FK を外し、`auth_user_id UUID`（FK なし）+ `subject_kind` で保持。purge されても行が残る
- (b) 匿名ユーザーは purge しない運用に変える
- (c) purge 前に同意ログを別テーブル（`consent_logs_archive`）へ退避する

当方の推奨は (a)。同意ログは本人の存在に依存しない独立した証拠であるべきで、CASCADE で消える設計自体が誤りだと考える。ただし既存ユーザー分の移行が要る。

### Q3. 再同意に応じない既存ユーザーをどう扱うか（§3-5）→ **(a)**

対象は現在20名。選択肢:

- (a) 次回ログイン時にモーダルを出し、同意するまで全機能をブロック
- (b) 猶予期間（例: 施行日まで）を設け、期間中は告知バナーのみ。期間後にブロック
- (c) 同意しない人は読み取り専用（記事閲覧のみ可、チャット不可）

越境移転の同意が新設されたため、同意なしにチャットを使わせると Gemini へ送信できない。つまり実質 (a) か (c)。当方の推奨は (a)。20名規模なら猶予期間の運用コストの方が高い。

### Q4. 施行日をいつにするか（§3-6）→ **実装完了と矛盾解消の後に決める**

1.1.0 のファイルには **2026年9月1日** を仮置きしてある。規約第11条の周知義務があるので、既存20名への告知から施行までの間隔を決める必要がある。実装完了見込みが立ってから確定したい。

### Q5. スクロール必須にするか（§3-7）→ **導入しない。全文を開いた記録を残す**

弁護士は「必須ではないが有用」。規約・プラポリは現在 3,000 文字超で、モバイルでは相当なスクロール量になる。当方の推奨は **導入しない**。代わりに「全文を開いたこと」を記録する（リンククリックの有無をログに残す）方が UX との釣り合いが良い。ただし証明力は落ちる。

### Q6. 賠償額の上限をこのままにするか → **このまま**

弁護士コメント: 「賠償額の上限規制の条項となりますので、適宜上限額を修正してご使用ください」。現行は「直前12か月間に実際に支払った利用料金の総額」。本サービスは現在無料なので、この上限は **実質0円** になる。有料化前提の条項が無料期間にそのまま効いている状態でよいか。

決定: このまま。残るリスク: 消費者向けの契約で事業者の賠償責任を全部免除する条項は消費者契約法8条で無効になりうるため、上限0円が争われた場合に条項ごと効かない可能性がある。有料化の設計時に弁護士へ上限額を相談する。

## 2. データモデル

### 2-1. `consent_logs` の独立化（Q2 = (a) で確定）

```
-- 現行
user_id UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE

-- 変更後
auth_user_id  UUID NOT NULL          -- FK なし。purge されても残す
subject_kind  TEXT NOT NULL          -- 'permanent' | 'anonymous'
```

既存行の移行: `auth_user_id := user_id`、`subject_kind := 'permanent'`（現状 anon は1行も無いため）。

インデックス: `idx_consent_logs_auth_user_id (auth_user_id, consented_at DESC)`。最新1件を引く `/api/consent/me` のクエリがこの形。

前方・後方互換性: `user_id` は即座に落とさず、1リリース分だけ両方書いて残す。ロールバック時に旧コードが `user_id` を読めるようにするため。

### 2-2. 「全文を開いた」記録（Q5 で確定）

```
terms_opened   BOOLEAN NOT NULL DEFAULT false
privacy_opened BOOLEAN NOT NULL DEFAULT false
```

### 2-3. RLS

007 は `consent_logs_self_insert` に `is_anonymous IS NOT TRUE` を足している。理由は「anon は同意フォームを踏まないので、書く正当な経路が無い」。匿名にも同意を課すなら、この前提が崩れるので述語を外す。

ただし実態として `/api/consent` は `getAdminClient()`（service_role）で書いており、RLS は現状この経路の関門になっていない。それでも Lesson 9 の「コードでも DB でも」に従い、ポリシーは意図と一致させる。**RLS を緩めるのは migration の中で最後、かつ単独の migration にする**（007/008 のドリフト事故＝Lesson 27 の再発を避けるため、適用後に `pg_policies` で実測 verify）。

## 3. API契約

### `POST /api/consent`（既存、変更あり）

現行スキーマに追加:

```
{ terms_version, privacy_version, age_verified: true,
  terms_opened?: boolean, privacy_opened?: boolean }
```

変更点は2つ。匿名ユーザーを弾かないこと（現状も弾いていないが、`requireAuth` は匿名セッションを通すので実質そのまま）と、`profiles.onboarded_at` の更新を匿名では行わないこと。匿名は `ensureProfile` で既に stamp 済みのため。

エラー:

- 401 `UNAUTHORIZED` セッション無し
- 400 `INVALID_INPUT` スキーマ不一致、`age_verified !== true`
- 409 `VERSION_MISMATCH` **新規**。送られてきた版が `CURRENT_*_VERSION` と違う場合。古い同意画面を開いたまま放置したタブからの送信を弾く
- 500 `INTERNAL_ERROR`

### `GET /api/consent/me`（既存、変更なし）

`isLatest` を既に返している。消費者がいないだけ。

### `POST /api/consent` の冪等性

同じ版で複数回叩かれたら行が増える。これは**意図的にそのまま**にする。同意ログは追記型の証拠であり、重複行があっても害はなく、むしろ「いつ同意画面を見たか」の記録になる。ユニーク制約は張らない。

## 4. 状態遷移と副作用

書き換えるデータ: `consent_logs` に1行 INSERT、`profiles.age_verified` を true、初回のみ `profiles.onboarded_at`。

外部副作用: なし。メール送信も外部API呼び出しも無い。既存20名への事前告知メールは**アプリ外の手作業**とする（20名なので自動化する価値が無く、自動送信は誤爆リスクだけ増える）。

再実行時の挙動: 上記のとおり追記。副作用が無いので安全。

## 5. トランザクション境界とロールバック範囲

現行実装は `consent_logs` INSERT →  `profiles` SELECT → `profiles` UPDATE の3クエリを個別に投げており、**トランザクションになっていない**。INSERT 成功後に UPDATE が落ちると、同意ログはあるのに `age_verified` が false のままになり、ユーザーは同意画面に戻される（同意ログだけ二重に積まれる）。

害は「重複行」だけで実害は無いが、直すなら RPC（`record_consent(...)`）に寄せて1トランザクションにする。今回の変更で `consent_logs` を触るので、**同じ migration で RPC 化するのが自然**。

外部副作用がトランザクション内に無いため、ロールバック範囲は DB に閉じる。

## 6. 認可ポリシー

認証: 必須（匿名セッションを含む）。

認可: `auth.uid()` と書き込み対象の `auth_user_id` の一致のみ。他人の同意ログを書く経路は無い。テナント概念は無いので越境の論点は発生しない。

注意点: `/api/consent` は service_role で書いているため、**アプリコードが `user.id` を取り違えたら RLS では止まらない**。`user.id` を body から取らず必ず `requireAuth()` の戻り値から取る、という現行の作りを維持する（body に user_id を足さない）。

## 7. 異常系シナリオ

1. **DB接続断（INSERT 前）** — 500 `INTERNAL_ERROR`。ユーザーは同意画面に留まり、再送信できる。副作用ゼロ。
2. **INSERT 成功後に profiles UPDATE が失敗** — §5 のとおり同意ログだけ残る。現状は 500 を返しユーザーは再試行 → 重複行。RPC 化すれば消える。
3. **版の不一致（古いタブからの送信）** — 409 `VERSION_MISMATCH`。画面をリロードさせる。これが無いと「1.0.0 に同意した」行が施行後に積まれ、`isLatest` が永久に false になってループする。
4. **同時更新の競合（2タブで同時に同意）** — 両方 INSERT される。ユニーク制約が無いので競合せず、`isLatest` は最新1件で判定するため結果は同じ。害なし。
5. **匿名ユーザーが同意後に本登録（signInAnonymously → FB OAuth）** — auth user id が変わるため、匿名時の同意ログは新アカウントに紐づかない。**本登録時に改めて同意を取る**。匿名の同意は匿名セッションの分だけを担保する、と割り切る。
6. **不正入力** — `age_verified: false` は Zod の `z.literal(true)` で 400。version 文字列に巨大値や制御文字 → 現行 `z.string().min(1)` は素通しするので、`z.enum([CURRENT_TERMS_VERSION])` に絞る（3 の 409 判定と同時に解決する）。
7. **purge により同意ログが消える** — Q2 の急所。(a) を採らない限り発生し続ける。

## 8. パフォーマンス想定

QPS: 同意はユーザー生涯に数回。ベータ20名では実質ゼロ。負荷の論点は無い。

`/api/consent/me` を再同意ゲートとして**全ページで叩くと**話が変わる。proxy.ts で毎リクエスト DB を引くのは Lesson 7 で既に負債として記録済みなので、**同じ轍を踏まない**。判定は以下に置く:

- サーバーコンポーネント（`(authed)/layout.tsx`）で1回だけ引く
- proxy.ts には足さない

N+1 は発生しない（1ユーザー1クエリ）。データ件数が10倍（200名）でも同じ。
